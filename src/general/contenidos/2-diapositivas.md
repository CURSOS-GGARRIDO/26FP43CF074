== 📚 Preparación y Bases
Enfoque centrado en la **fase teórica y organizativa**.

- PI1: Conceptos refuerzan o complementando los conocimientos de módulos.
- PI2: Proyecto mínimo viable (MVP) con tecnologías actuales del sector.

== 💻 Prácticay Ejecución
Enfoque centrado en la **ejecución técnica**.

- PI1: aplicación básica con conocimientos mínimos para segundo curso.
- PI2: aplicación de infraestructura completa usando tecnologías de empresa.

## Diseño Integrador y Selección de Criterios

::: info-box Proceso de Configuración

- **1. Planteamiento:** Se diseña un proyecto final estructurado en base a los contenidos de cada módulo del ciclo.
- **2. Extracción:** Una vez definido el proyecto, se seleccionan e integran únicamente los **Resultados de Aprendizaje (RA)** y **Criterios de Evaluación (CE)** más relevantes y aplicables a la solución planteada.
:::

::: accent-box teal 💡 Independencia Evaluativa
**Regla fundamental:** Aunque los RA y CE se extraen del currículo general, su calificación en esta fase es **totalmente independiente**. El alumno demuestra estas competencias aplicadas al proyecto final, al margen de la nota teórica o práctica que haya obtenido en los módulos de origen.
:::

## Metodología y Evaluación PI2

> **ABP (Aprendizaje Basado en Proyectos):**

::: info-box Desglose de la Calificación

- **40% Proyecto:** Implementación técnica y funcionalidad.
- **20% Documentación:** Calidad técnica y memoria descriptiva.
- **20% Defensa:** Exposición oral y debate técnico.
- **10% Participación:** Implicación en mesa redonda, tutorías, etc.
- **10% PI1:** Nota de la fase previa.

## Visión, Requisitos y Planificación Ágil

> "El MVP debe resolver el problema principal con el mínimo esfuerzo posible, diferenciando estrictamente lo vital de lo accesorio."
>
> — *Filosofía Lean & Agile*

::: tabs

== 🚀 Visión y MVP

- **Lean Canvas:** Plan de negocio en una página.
- **Roles:** Product Owner, Scrum Master, Development Team.
- **MoSCoW:** Priorización de requisitos (Must, Should, Could, Won't).

== 📋 Historias y Backlog

- **Estructura INVEST:** "Como [Rol], quiero [Acción] para [Beneficio]".
- **Estimación:** Story Points (Planning Poker).
- **Criterios:** Definition of Ready (DoR) y Definition of Done (DoD).

== 🔄 Sprints

- **Iteraciones:** Flujo continuo: Planning → Dailies → Review → Retrospective.
- **Seguimiento:** Si es individual, se exige un *Diario de Desarrollo* cada 3 días.

:::

## Ecosistema Git y Docs-as-Code

![Git](/img/contenidos/general/diapositivas/07.png)

::: tabs

== 🌳 Ramificación y PRs
Uso de Trunk-Based o Git Flow. La rama **main** siempre está protegida. El código se integra obligatoriamente mediante **Pull Requests (PRs)** validadas por pares.

== 📝 Commits Semánticos
Historial comprensible usando el estándar **Conventional Commits** (ej. **feat:**, **fix:**, **docs:**). Permite auditoría del trabajo diario.

== 📖 Documentación Viva
Filosofía **Docs-as-Code**: Toda la documentación reside en Markdown (**md**) junto al código. Los esquemas se generan directamente con código usando *Mermaid*.
> ![Edupress](/img/contenidos/general/diapositivas/image.png)

:::

## Calidad, Testing y Cierre

::: accent-box purple 📝 Finalización del Ciclo
Antes del despliegue final, el código debe ser validado y reflexionado.
:::

::: info-box Pirámide de Testing

- → **Unitarias:** Pruebas rápidas de funciones aisladas (Principio FIRST).
- → **Integración:** Pruebas de comunicación entre los módulos internos o APIs.
- → **E2E (End-to-End):** Simulación automatizada del usuario final (ej. Cypress).
:::
